## Project overview

Shared, app-independent technology for secure device-to-device data sync in Tobias' offline-first web
apps: a signed gapless change log per device, end-to-end encrypted transfer, device trust and
invitation, a relay client and Web Push helpers. Created 2026-11-21 (decision: extract it from the
apps that carry copies of it). **Status: 0.0.0, core layer (incl. end-to-end session, encrypted file and sealed envelope), post layer (mailbox, per-day exchange, receipts), log layer incl. signing and exchange protocol (parsers, session, fingerprint), trust layer, relay layer (client, strict readers, framing, protocol document, conformance cases), transfer layer (fountain QR frames, tone messages, direct connection by exchanged texts), push layer (ring request, Web Push encryption, VAPID, service worker template), browser layer (IndexedDB key store, credential store, one listener per tab, camera and audio interfaces), not
published to npm. GitHub repo made public on 2026-11-21 (Tobias' OK); the README carries a "Not security-reviewed by a human" notice until a human security review is done (four adversarial AI review rounds so far).**

**The inventory of the existing implementations, the measured drift between them and the plan (names
private projects) live in the private companion repo `device-sync-privat`**
(`private/device-sync-privat/docs/`). Never name those projects in this public repo
(`tests/coupling.test.ts` fails if they appear).

**Platform:** browser (and WebView2); no Expo/React Native
**Language:** TypeScript
**Architecture:** layers `core`, `log`, `trust`, `post`, `relay`, `transfer`, `push`, `browser`
(`docs/architecture.md`). Pure layers take clock and randomness as parameters. App things are
parameters, hooks or strategies (`appId`, limits, who may vouch, right to write, hold-back hook).
Errors are codes, not sentences.

## Key rules

- **Public repo in the end (AGPLv3 + commercial):** no app data, no real names, no private project
  names in files or git history. The first commit is neutral.
- **The repo is public (since 2026-11-21, Tobias' OK), the work is in the open.** Nothing is published to
  npm or tagged for use, and the README's "Not security-reviewed" notice stays, until Tobias says so after a
  security review (threat model, fuzzing of the strict parsers, independent pass). Never commit keys
  other than throw-away test keys; commit messages follow the same no-private-names rule as files.
- Crypto code changes only with the tests that guard it; ported code keeps the tests of both source
  implementations (their union).
- The other apps are not converted from here; they get a note to check the package.

## Known Limitations

- Only the first part of the core layer (encoding, canonical JSON, markers, device keys, check code) and the log layer (change model, merge, redaction, notices, history, undo, signing, exchange protocol with strict parsers) exist; the trust layer (device list, derivation, meeting code, invitation) exists; the end-to-end session and the encrypted file (core) exist; the sealed envelope (core) and the post layer (mailbox, exchange, receipts) exist; the relay layer (client, readers, framing, conformance) exists; the push layer (ring request, Web Push encryption, VAPID, service worker template) exists; the browser layer (key store, credential store, one listener per tab, camera and audio interfaces) exists; the transfer layer (fountain QR frames, tone messages, direct connection by exchanged texts) exists; group keys are not implemented.
- Exchange: pieces are meant to arrive in order. A reordered session may not take everything but never corrupts a replica, and the next session fills the gap (`tests/log/order.test.ts`); in `receiveJudged` the pieces before the last may come in any order. `receiveJudged` judges each piece as it arrives and holds verified changes and changes whose author cannot be checked yet, bounded by `maxSessionChanges` and `maxSessionChars` in all; what is still unverifiable after the key-learning rounds is cut at `maxPendingChanges` and must come again. Limits never refuse: a sender cuts its answer to a prefix of its own log (`more: true`), a receiver ends the reading (`Session.truncated`) and takes what it verified, the next session continues (partial sessions; `outcome().complete` is false meanwhile; the judging state of a session is extended in place, so a `Session` value is never fed twice). Only hostile input is a refusal. The log itself is unbounded: an app bounds a flooding member with `mayWrite` and the `quota` hook (default unlimited). A stand is answered only with signed changes (`signedOnly`); a second `stand` or `done` ends the session. The fingerprint (128 bits) is a consistency check, not a proof against a peer that lies. Apps pass their own device id pattern (`deviceId` option); the default is permissive. A transport should cap message size before the parser; `parseSyncMessageText` refuses text over twice `maxMessageChars` itself.
- Performance: a batch merge is linear (6000 changes to 6000 records in about 15 ms; `tests/log/batch.test.ts`); notices and final deletions use a per-record index of the log (`recordIndex`), so 8000 writes of one device to a 40-field record merge in well under a second and 20000 deletions likewise (`tests/log/performance.test.ts`). Every merge still copies the log and the collection of the touched records (O(records) per local write: about 11 ms at 20000 records in one collection); the index is kept per log array (a log rebuilt by hand is indexed again on first use). Pairs of heads of one field are compared pairwise, so a field written by thousands of different devices is quadratic in the devices. Replicas are immutable values: the per-log caches are checked against array length and last element, a middle entry changed in place is not noticed. Verifying 12000 new signatures costs about 2 s of crypto in any case (`tests/log/review3.test.ts`); a repeat of a change the replica already holds is not verified again.
- Conflict notices are derived from the log (a change against the earlier implementations, which built them incrementally and could differ between devices); a notice lists the concurrent heads, not every superseded write.
- Hold back until approved (`docs/approval.md`): **new, not yet reviewed**. `mergeApproved` / `SessionOptions.approval` ask an app hook (`apply`/`hold`/`reject`) per new `set`/`delete`; held changes live in `Replica.approval` outside log and vector (no stand claims them); a rejected write becomes an erased change that keeps its number and is never forwarded (`Session.withheld`); a final deletion can only be held or approved; the state has a strict reader and the bounds `maxPending`/`maxChars`. Convergence needs a hook that answers from the change alone; judging assumes everything applies (hold a device's `addDevice` too); equivocation against a held change is not seen.
- Round 5 (AI pass, still no human review): session, file, envelope, post, relay, push, transfer and browser were reviewed. Only the last `ids`/`envelopes` message of a post exchange may be empty; `isKnownEnvelope(value, appId, limits?)` checks remembered size and fan count; `sealEnvelope` refuses a non-signing key with `bad-author`; `openSession` refuses the static pair as the ephemeral pair (`bad-own`); `readSdp` refuses a bare CR/LF and several distinct DTLS fingerprints; the direct inbox is bounded by `inboxMax` and `inboxBytesMax`; service worker URLs refuse a backslash; the relay client refuses a redirected answer (credentials are not bound to the relay origin: one store per relay); a throwing frame reader does not stop the camera loop.
- Real browser: `npm run test:browser` runs 24 tests in real Chromium (IndexedDB, Web Locks, BroadcastChannel, Web Audio, fake camera and microphone, two `RTCPeerConnection`s, a real service worker with a real push event); not in CI. Not run: Firefox, Safari, mobile browsers, WebView2, a real push service, real QR scanning, tones over a speaker, STUN/TURN or two devices. The older 'never run in a real browser' sentences below are superseded by this line.
- The soft-delete field name `deleted` is reserved. Local writing refuses what the parser refuses (names, values, limits); `knew` names only the unresolved concurrent heads of the fields, so a field written by many devices one after another stays writable; more than `maxDevices` unresolved concurrent heads give `too-many-devices` until someone resolves them.
- A change that names a `knew` the receiver never reaches (a liar, or a change whose dependencies were lost) is held for good, with everything later from its author; only its own author is blocked. Held changes are not stored: the sender must send them again. `merge` takes `set`/`delete` changes without `knew` as held; the parser refuses them. Canonical JSON throws `TypeError` for anything that is not plain JSON (a top-level `undefined` is still `null`).
- Trust: the invitation text carries no signature; the inviter's keys in it are only as trustworthy as the channel (compare check codes; use `checkCode(..., groups)` with 8 or more groups where the code is the only protection against a modified link). **Removal ends a device's standing as a voucher and as a device that can be introduced through the chain. The device stays `checkable`, and so does every device whose key was ever validly vouched for and that fell out of trust without being removed (vouched only through a removed device): `checkable` is every device of the potential trust without a key conflict (a device with a key conflict, or with a signing key the removed vouchers disagree on, is not checkable). Their signed changes (earlier AND later) verify and are accepted by the signature layer; this layer does NOT revoke anybody's ability to write** (the automatic write cut-off, `lastSeq`, the verdict `ignored` and `KeySource.standing` were taken out: a device-local cut-off made honest devices disagree and block each other; what holds is exactly: no honest device is held back for ever by changes of a device that fell out of trust, and a verdict does not depend on what `merge` currently holds, `tests/trust/round4.test.ts`). An app stops exchanging with a removed device at the transport, treats data authored by untrusted devices as untrusted at presentation (`deviceStatus`), restricts writes with `mayWrite` / `allowFinalDelete` (hooks that look at state can answer differently on two devices) and, once the encryption layer exists, rotates the group keys on removal. A removed id stays removed: re-admission is a new device id (`addDevice` refuses `removed`; `removed: false` is never a way back). **Removals are evaluated rank by rank (distance from the met devices), all devices of one rank at once, with NO tie-break by device id** (a joining device chooses its own id): two equal-rank devices that remove each other are both removed. A removal persists after the remover is itself removed by a device of the same or a higher rank; only a device of lower rank can undo the damage (by removing the remover). Any voucher can remove the devices it can reach (inherent in the voucher strategy: choose `vouchRoles`). The result depends on the viewer's devices met in person (`direct`): a viewer who met B in person and one who knows B only through the chain can disagree about who is trusted, by design (`tests/trust/round4.test.ts`, F6). What a removed device wrote carries no authority for key conflicts and it does not vouch, so a compromised voucher cannot poison other entries once it is removed; while it is NOT removed, a voucher that writes other keys into another entry still makes that entry untrusted through the chain (`key-conflict`) and conflicting relay ids are dropped. At most `MAX_CANDIDATE_KEYS` (8) signing keys are tried per entry (the newest), so a voucher that writes many keys cannot make a derivation cost keys times writes; a voucher that writes more than 8 keys into an entry can make that entry's own writes unverifiable until it is removed. A voucher can pre-occupy a future device id with its own keys (`addDevice` of the real device then answers `other-keys`), and `listDevices` shows raw entries (self-written roles included): never authorization. Potential trust only grows: a voucher that is later given another role stops vouching, but what it introduced while it vouched stays in P. `canVouch` is asked when a device joins and when its entry changes (answer from the entry), the number of rounds is bounded. The derivation is linear (400-device chain: 7 ms warm), every new replica state is derived again (index per log array); `readChanges` of a 1599-change chain takes about 0.6 s because `deviceKeySource` is `selfVerifying` (the key source is asked against the replica plus the waiting changes and the verified ones merge holds back, never one claiming the receiver's own id). `addDevice`/`removeDevice` decide on this device's own log as judged (no signature is checked again). Not ported: the 'confirmed role' flag of one earlier implementation, the device lock after days without contact, relay/session wiring. Parsers are stricter than the earlier ones (one spelling only, unknown members refused).
- Trust, accepted: the meeting code carries role and name as self-declaration, has no recipient bound and can be relayed by a third party within its 120 s window. The single use of an invitation is not enforceable offline (two replies to one code can both be taken; the damage is one more device of that role): an app keeps a ledger of used invitations; a removed device re-enters only through a fresh invitation with a new device id. A vouching device (an administrator) can still choose any name or role for an entry. A removal can only be undone by a new device id, never by writing `removed: false`.
- Equivocation (one device number signed twice) is seen with a hash chain: every change after the first carries `prev` (the LINK of the same device's previous change: a hash of its whole signed head, so a version that differs in any signed member has another link; kept by an erased change) and a `stand` carries `tips` (per device the link of the change at its vector position). Two devices holding different versions of one number, or of any earlier number, end the first session they hold both with the refusal `diverged` and the reason `tip-mismatch`. **A tip is an unproven claim**: that reason names no culprit (`Session.subjectDevice` is the device whose history differs, `refusalDevice` stays unset), because a forged tip would otherwise make an app remove an innocent device. The one proof an app may act on is `proveEquivocation(a, b, publicKey, appId, dataSet)` for two changes of one device and number with different signed texts that both verify (fetch the other version with `changeAt` from the device that holds it); the verdict `equivocation` stays only where two signed changes are in hand (a successor whose `prev` names another version than the held predecessor). Not detected: two versions held by replicas that never meet, and a double signature nobody holds both halves of. A device that took the harmless version keeps refusing the erased write of the other (`redacted-without-deletion`). A device restored from an old backup gets `own-history` (only for a change that really carries its own signature) and must re-enrol with a new device id. Format change: the link (and so `prev` and the tips) is now the hash of the signed head, not the content check value; the signed text itself is unchanged; `tests/vectors/` were extended (`chain.json`) on purpose.
- Partial sessions: an answer to a stand always holds at least one applicable group of changes (an erased change, its author's earlier numbers and the deletion are one group), also when that group is larger than the budget, and the receiver reads past the budget while an erased change waits for its deletion (up to `maxGroupChanges` / `maxGroupChars`) and always takes the first change of a session; an indivisible group larger than those ceilings cannot be taken (the session ends `truncated` every time: raise the limits). A stand or done of more than `maxStandDevices` (10000, and not over `maxMessageChars`) devices ends the session gracefully (`truncated`, `limit: 'stand-devices'`). An identical repeat of a stand or done is ignored. A partial session cut (`more`) can delay an erased change until the next session; an erased change without any deletion in sight in a partial session waits instead of being refused. The fixpoint that decides which erased changes count is found with one linear pass over the dependencies plus a few merges.
- A final deletion is judged false unless the app passes `allowFinalDelete`. Signatures are low-s only (a high-s twin is refused); the check code carries about 66 bits. JSON texts with duplicate keys and strings with lone surrogates are refused (cross-language rules in `docs/wire-format.md`, vectors in `tests/vectors/`).
- Session and encrypted file (`docs/wire-format.md`, "Wire format: end-to-end layer"): **new, not yet reviewed** (the four review rounds were before them). The session is NOT resumable (counters are the nonces and live in memory only; after a restart make new hellos, never restore an old counter); one ephemeral pair opens one session (remembered per process only); a dropped last message is not noticed and a gap ends the stream (start a new session, nothing is retransmitted); no ratchet, so a leaked session key opens that session; no padding (length, counter and timing show); the hello carries the device id in clear and is not authenticated (a replaced hello only makes the session fail); forward secrecy needs the ephemeral pair to be discarded (JavaScript cannot wipe memory). The file has no forward secrecy against the recipient's static key, whoever holds that key can forge a file "from" anybody to it, there is no replay protection or freshness (the app must be idempotent), sender, recipient and app id are in clear in the header. Payloads are opaque bytes (the app serialises; no `canonical` here). Both layers take the peer's agreement key from the caller: whether it belongs to the right person is the trust layer's job. `isPoint` now accepts only the canonical spelling of a point (before, a second spelling of the same key gave a second check code); a reader refuses a byte order mark in front of a file (`TextDecoder` would have dropped it silently).
- Envelope and mailbox (`docs/wire-format.md`, "Wire format: envelope and mailbox"): **new, not yet reviewed**. The envelope hides sender, readers and their number (up to a multiple of 8 slots, at most `maxFans` = 64) from a carrier; it does NOT hide size, day, id or the carrier path, the author is not deniable (any reader can prove who wrote it), a reader can re-seal what it read, there is no replay protection (apps must be idempotent), no forward secrecy against a reader's static key, and a carrier can drop, delay or multiply an envelope. The content is opaque bytes (the app puts its stand and changes in it); the package does not look inside. Sealing draws one ephemeral key from WebCrypto besides the `random(n)` the caller passes. A mailbox holds at most 2000 envelopes / 8 000 000 characters, expires after 30 days, takes at most 400 new envelopes a day from one other device (the newest days first) and counts at most 256 such devices a day; a neighbour can still use up its own quota with junk and push older real envelopes out of a full mailbox. Receipts are the app's: the package drops only what a receipt of a device accepted by the app's predicate covers (a compromised allowed device can make carriers drop early). `addEnvelopes` takes at most `maxEnvelopes` envelopes per call (one call per batch; calling once per envelope copies the mailbox each time). The exchange expects the other side's messages in order and ends with a refusal otherwise; it does not resume, the next meeting starts again. Format version 2: the earlier implementations' bytes are not readable (marker, id, day check values (128 bit instead of 32), header and slot info texts differ on purpose).
- Relay layer (`docs/relay-protocol.md`): **new, not yet reviewed**. It speaks protocol version 1 of the existing relay servers, whose endpoint names, member names and error kinds are German words (kept exactly on the wire, English in the API). The later admission revision of those servers (certificates, groups, roles, listing and blocking) is not implemented. The document lists the open points of version 1 that a server owner still has to decide (version negotiation, servers without shared memory, restart behaviour, order of simultaneous errors, unusual JSON, retry hints). The relay sees app, device ids, sizes, timing and the push endpoint of a ring; it can drop, delay, duplicate or reorder messages; whoever holds its signing secret can enrol or impersonate a device. A collect whose answer is lost has already deleted its messages (the relay keeps nothing), and a drop is never repeated after an unclear outcome: apps must be idempotent. The conformance cases need the optional test interface (clock, limits, push stand-in, reset) for 9 of 70 cases; the runner skips those without it, and a case that would need more than 50 devices of one app is arranged to avoid it. The reference server and the cases were written from the document and the server source, not run against the real servers (not verified). The framing convention (`framing.ts`) is the package's own, not part of the relay protocol; the credential store and the one-listener-per-tab election are in the browser layer; a browser connection is not implemented.
- Public but unreviewed: the README says so; no npm release and no tag for use before the security review.
- Push layer (`docs/push.md`): **new, not yet reviewed**. A ring carries no content: the push service sees timing, endpoint and the size of the encrypted body (padding only blurs it), the relay sees the endpoint, and anyone who holds a subscription can send a push to it (a forged push only makes a device look at its authenticated relay). No replay protection; the salt must be fresh per message and is only taken as a parameter. One ephemeral agreement key per message comes from WebCrypto unless passed in. Encryption is one record only (`rs` 18 to 4096; a longer message is refused as `multiple-records`); `checkVapid` is stricter than RFC 8292 (one spelling). `readSubscription` checks the shape of the receiver key, the curve check happens when the message is encrypted. The RFC vectors and an independent `node:crypto` implementation agree with the code, but nothing was run against a real push service (FCM, Mozilla, Apple, Windows). The service worker template was tested only in a `node:vm` sandbox with a fake scope, not in a browser (no real `showNotification`, `clients` or lock screen); a browser may show its own notice when a push arrives while the page is open.
- Browser layer (`docs/browser.md`): **new, not yet reviewed, never run in a real browser** (tests use an in-memory IndexedDB, a Web Locks manager, a channel, a virtual clock and a `MediaDevices` written for this repository). Keys are stored as non-extractable `CryptoKey` objects: no backup and no export, a cleared or vanished store means a lost device that re-enrols with a NEW device id (never new keys under the old id); any script of the origin can use (not export) the keys while the page runs; nothing is encrypted at rest; the layer does not ask for persistent storage. A database written by a newer schema is refused, not migrated. The channel election (fallback when there are no Web Locks) assumes one clock, a message delay of at most `delayMs` and timers at most `lateMs` late; a tab paused longer can lose the lead and win it back, a new tab waits a full `timeoutMs` before it may lead, and the proof is a sketch tested by seeded simulations, not a formal one; prefer Web Locks. Camera and audio are interfaces plus an adapter that maps errors to codes; the frame reader and the audio graph are the app's, and the QR or tone coding is in the transfer layer.

- Transfer layer (`docs/transfer.md`): **new, not yet reviewed, never run in a real browser** (no camera, microphone or `RTCPeerConnection` was used: the tests use an in-memory peer pair, synthetic samples and a virtual clock). It carries opaque bytes and authenticates nothing: its check values are CRC-32 (damage and another app's frames, not an attacker), anybody who sees the QR codes or hears the tones has the payload, and the direct-connection texts contain the device's IP addresses and a DTLS fingerprint that the app should bind to an authenticated session of the core layer. The three formats (frame, tone message, texts) are new and not compatible with the earlier implementations' bytes. No QR drawing or scanning, no TURN, no trickle ICE, no reconnection. A receiver stays with its first transfer unless it was made with `switchOnOther` (a forged frame can make it lose progress, costing time only). A tone message holds at most 16 octets and takes about 5 s per copy; the ultrasonic plan needs 44.1 kHz or more and many phones filter it. The handshake needs a clock that does not jump back.
